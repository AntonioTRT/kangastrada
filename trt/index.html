Selected work / Flagship engineering project

TRT

An integrated embedded engineering platform connecting autonomous board firmware, a cross-platform command-line interface, and modular hardware.

System overview

One runtime. Multiple boards. A consistent protocol.

TRT (Tool Runtime Terminal) is a portable runtime and tooling architecture for communicating with embedded boards. The host CLI issues typed commands through the shared TRT protocol; TRT-core routes them into a board implementation, which connects the runtime to its hardware and peripherals.

TRT-cli → TRT Protocol → TRT-core → Board implementation → Hardware

Boards are designed to remain autonomous: communication is an interface to the runtime, not the owner of its control loop. The architecture targets Arduino, ESP32, STM32, RP2040, simulator, and future compatible platforms through shared contracts and declared capabilities.

Core logic & firmware

TRT-core

A portable, cooperative embedded runtime.

TRT-core provides the shared runtime between protocol communication and board-specific integrations. Its architecture is organized around a configuration manager, state machine, services, event and command systems, protocol integration, transport interfaces, and capability management.

The cooperative execution model updates services, processes events and commands, advances state, and transmits queued messages without blocking on host input. Board adapters provide peripheral drivers and platform-specific behavior; the core depends on interfaces rather than board-family checks.

  • Queued command and event flow
  • Non-blocking runtime
  • State machine
  • Capability declarations
  • Board and transport interfaces

Protocol V0.1 baseline

The mandatory compatibility commands are PING, FW_VERSION, BOARD_VERSION, INFO, STATUS, and CAPABILITIES. Responses use ACK, NACK, or DATA frames, with defined errors for unknown or unsupported commands, invalid arguments, busy devices, timeouts, and internal failures. The current core implementation reserves the CRC16 field as 0x0000.

Tooling & interface

TRT-cli

A single workflow from discovery to diagnostics.

The Python command-line interface separates Typer command handlers and Rich terminal output from application services, typed protocol clients, transport implementations, and board-state storage. Serial discovery probes available ports for compatible boards; discovered board IDs, ports, and baud rates can be cached for later commands.

  • Board discovery and information
  • Capabilities and status
  • Heartbeat listening
  • Serial diagnostics
  • STM32 build and flash workflows

Heartbeat listening provides a passive runtime check: TRT-core boards emit a HEARTBEAT event approximately once per second. The CLI retains mock transport for explicit test and support use; it is not the path used for the validated board-information transaction.

Hardware & physical layer

TRT_HW

A modular carrier-board design.

The documented carrier-board specification is based on an STM32G474RET6 ARM Cortex-M4F microcontroller, rated up to 170 MHz with FPU and DSP. A 2×8 board-to-board connector brings power, GPIO, SPI, I2C, and four digital hardware-identification signals to daughterboards.

POWER & DEBUG

Bring-up access

USB-C 5 V input, an AMS1117 3.3 V regulator, reset circuitry, and Tag-Connect SWD for programming and debug.

BUSES & I/O

Peripheral interfaces

SPI1 and I2C1 connect through the expansion header. I2C pull-ups are switchable for low-power operation; GPIO, DAC, and HWID signals support board integration.

LOAD CONTROL

PWM motor driver

An AO3400A low-side MOSFET stage, flyback diode, and dedicated motor connector provide a documented interface for PWM-controlled loads.

The hardware README specifies a 10 kHz motor PWM setup and layout guidance for power-current return paths, MCU decoupling, the 8 MHz crystal, and the USB differential pair. These are design and integration requirements, not reported hardware test results.

For the separate NUCLEO-L073RZ firmware integration, the documented bring-up procedure is to build and upload with PlatformIO, connect through the ST-LINK virtual COM port at 115200 baud, and send a protocol PING that should return ACK for board 0x0002. Follow-up checks use TRT discovery and board-info commands, observe the LD2 heartbeat at 500 ms, and confirm the B1 button changes the blink interval to 100 ms. This NUCLEO target is distinct from the STM32G474 carrier-board design above.

Project status & milestones

From protocol contract to real hardware.

The current milestone combines a defined protocol baseline, implemented developer workflows, and documented board integrations.

01 / PROTOCOL

Compatibility baseline defined

Protocol V0.1 specifies six required board commands, standard response types, and error identifiers for interoperability.

02 / END-TO-END

Arduino Uno transaction validated

TRT-cli 1.0.0 communicated over COM4 with an Arduino Uno running TRT-core. The validated board-info response reported board ID 101, firmware 0.1.0, and build ID 000004.

03 / STM32

Build and flash workflows implemented

CLI support for STM32 build, flash, program discovery, and protocol tests is documented. Toolchain- and probe-dependent verification requires the corresponding local tools and target hardware.

Verification boundary

Design specifications are not bench results.

The STM32G474 carrier-board README documents the circuit, pinout, firmware integration guidance, and PCB layout checks. It does not report completed fabrication or validation results for that carrier board. The verified end-to-end board transaction documented by TRT-cli is on the Arduino Uno target.
